# Game UI Generation

Generate the game-owned UI implementation for one task inside the prepared
workspace.

## Inputs

Read all provided context before editing:

- the prepared UI task packet and task-specific requirement;
- the general game requirement, when present;
- the target Engine identifier;
- the API Context target identifier;
- the explicit ordered delivery plan;
- the read-only Engine Context directory;
- the completed Mechanic artifact and its metadata;
- the mandatory versioned `mechanic_contract.json`;
- the public Mechanic runtime adapter paths selected from the finalized
  artifact;
- the declared Mechanic state, event, and command bindings for an
  engine-native task;
- the game design document and general game requirement;
- required screens, view constraints, and forbidden UI;
- high-priority reference images, when provided;
- optional read-only examples;
- this Skill.

The requirement defines presentation. The Mechanic artifact owns game rules,
state, events, and commands. The Pipeline deterministically selects the exact
Engine and Browser Serving API documents. Read those paths from the packet;
do not select alternatives.

## Ordered UI Delivery

UI generation is a mandatory two-stage process. Every UI task MUST generate:

1. the `engine_native` UI implementation;
2. the `browser_play` serving implementation.

The second stage depends on the first stage. A UI task is incomplete if either
stage is missing. Complete both stages in order for the same UI task.

### Engine-Native Mechanic UI

The `engine_native` stage is the real Mechanic-facing game UI and is generated
first. The Agent must:

1. Read the Pipeline-selected concrete Engine API document.
2. Read the finalized generated Mechanic artifact, mandatory
   `mechanic_contract.json`, metadata, and supplied Public contract source
   paths.
3. Inspect every supplied matching engine Example path. For UE this normally
   includes both the Mechanic Example plugin and its dependent UI Example
   plugin, such as `FPSExample` plus `FPSUIExample`.
4. Generate engine-native, game-owned HUD/widget/menu/plugin source that binds
   to the generated Mechanic's public state/events/commands.
5. Follow the concrete engine's module, package, plugin, lifecycle, input,
   rendering, and testing conventions from the selected Engine API and
   Examples.

The generated Mechanic artifact is authoritative. Engine Examples demonstrate
valid engine-native structure and public-contract consumption, but they are
read-only references and must not become generated-game dependencies.

### Browser Play UI

The `browser_play` stage follows after the engine-native UI plugin is complete.
It is the Web Play mapping and delivery surface around the completed engine
game:

```text
engine-rendered view + assets + sessions + generic controls
    -> Browser Serving API
    -> Web frontend
```

Browser Serving does not replace the engine-native HUD/UI and does not own
Mechanic presentation. The streamed engine frame already contains the
engine-native HUD generated by the earlier engine-native UI task.

The current Browser Serving API maps:

- engine stream/view embedding;
- engine and connection status;
- asset upload, inspection, and selection;
- Avatar/Motion/World selection;
- session create, preview, Play, leave, and stop;
- normalized input forwarding.

It does not currently expose a public versioned Mechanic state/event/command
bridge for Web-native gameplay HUDs. Therefore a browser UI task must not
invent health, ammo, score, objective, victory, pause, or other Mechanic UI in
HTML/JavaScript. Such UI remains engine-native unless a future implemented
Serving contract explicitly publishes the same Mechanic contract to Web.

The single UI task uses this fixed order:

```text
Mechanic + engine-native UI plugin
    -> runnable engine game
    -> Browser Serving API
    -> Browser Play UI
```

Keep the stage outputs separated: engine-native plugin/source stays under the
main `generated_ui/` tree, while Browser Play source stays under
`generated_ui/browser_play/`. Do not mix the concrete Engine API and Browser
Serving API inside either stage.

## Input Authority

Apply each input to the dimension it owns:

1. During `engine_native`, the Mechanic contract is authoritative for available
   state, events, and commands. Never invent a missing Mechanic surface. For
   `browser_play`, Mechanic binding lists and Public source paths in that stage
   of the delivery plan must be empty.
2. The UI requirement, acceptance criteria, required screens, view
   constraints, and forbidden UI are authoritative for UI behavior and
   acceptance.
3. Supplied reference images are high-priority visual truth for composition,
   hierarchy, density, spacing, color, typography, and style. Inspect every
   supplied image before implementation.
4. The design document and general requirement define product intent, genre,
   world, tone, and cross-screen consistency.
5. Supplied engine Examples are required structural references for
   engine-native UI, but remain lower authority than the selected Engine API,
   finalized Mechanic contract, requirements, and acceptance criteria.

Reference images do not override forbidden UI, explicit acceptance criteria,
accessibility, text fit, protected view regions, or the Mechanic contract. If
an explicit conflict requires a visual deviation, preserve the higher
authority and report the deviation.

## Pipeline-Selected API Contexts

1. Read `selected_api_contexts` from the prepared task packet.
2. Read the selected concrete Engine API before `engine_native`.
3. Read the Pipeline-selected Browser Serving API before `browser_play`.
   The Pipeline-selected Browser Serving API is authoritative for that stage.
4. Do not replace either path, read unrelated API documents, or mix APIs.
5. If a selected document is unavailable, report the missing context.

## Browser Play Mapping

After the engine-native plugin is complete, for `browser_play`:

- read the Pipeline-selected Browser Serving API;
- consume only the public HTTP/WebSocket API documented there;
- keep game-owned browser source under `generated_ui/browser_play/`;
- preserve the documented asset-admin and player routes, control IDs, and
  session semantics;
- do not import a concrete engine package from browser UI source;
- do not add concrete-engine branches to the frontend;
- do not copy engine process launch, asset import, stream transport, or
  backend implementation logic into generated UI;
- do not inspect or consume Mechanic Public source paths;
- do not declare Mechanic state, event, or command bindings;
- do not generate a mocked Mechanic contract fixture;
- do not generate a second Web-native gameplay HUD from Mechanic fields. The
  engine-native HUD remains inside the streamed engine view.

Browser Play is limited to the engine stream/view plus connection, asset,
World, session, Play, and generic input controls. It MUST NOT reproduce
gameplay HUD, gameplay state visualization, or Mechanic commands in HTML,
CSS, or JavaScript.

Use the selected Browser Serving API to map the engine stream, assets, worlds,
sessions, preview, Play, leave, stop, and normalized input into the Web UI.
The engine identifier is backend selection data, not a reason to add
engine-specific browser code.

When the selected engine has no registered Browser Serving backend, report the
integration gap. Do not edit adapter-owned framework source from a normal UI
generation task.

## Mechanic Binding

- For `engine_native`, bind the generated engine-native UI directly to the
  generated Mechanic's supplied Public contract source using the selected
  Engine API's supported dependency mechanism.
- Query state, subscribe to events, and invoke commands only through the
  public Mechanic runtime adapter. Never dereference a contract entry's
  producer-side `source` metadata as a gameplay object/property path.
- For `browser_play`, binding lists and Mechanic Public paths must be empty.
  Do not render Mechanic state or invoke Mechanic commands.
- Treat the Mechanic artifact as read-only.
- Read the mandatory root `mechanic_contract.json` before UI design or source
  edits.
- Bind only to task-declared state, event, and command names that exist in the
  contract.
- Inspect only contract-specific Public source paths supplied in the task
  packet. Do not browse arbitrary Mechanic implementation source.
- Bind only to declared state, event, and command surfaces.
- Do not bind to incidental private Pawn, Character, Controller, component,
  inventory, weapon, or vehicle implementation fields.
- Do not cast to concrete gameplay Pawn, Character, Controller, GameMode,
  weapon, or vehicle implementation classes.
- Do not reimplement game rules, state transitions, damage, movement, combat,
  racing, scoring, or other Mechanic behavior.
- Invoke gameplay actions only through declared Mechanic commands.
- Do not add UI for features forbidden by the task.
- If any required binding is absent from the contract, stop and report the
  contract gap instead of implementing a fallback rule.
- Do not create a local replacement Mechanic contract, empty interface,
  placeholder provider, stub state source, fallback state store, or duplicate
  state/event/command definitions.
- Do not copy the Mechanic contract into `generated_ui/`. Include or consume
  the read-only public contract through the selected Engine's supported
  dependency mechanism.
- Mock Mechanic data is allowed only in generated UI test fixtures. Runtime UI
  source must never use the mock fixture as a fallback.

The required dependency direction is:

```text
UI
    -> mechanic_contract
    -> public runtime adapter
    -> gameplay implementation
```

Direct access such as `Character->Health`, `Weapon->Ammo`, or private gameplay
casts is forbidden.

## Workflow

1. Read the explicit ordered delivery plan from the prepared task packet.
2. Complete `engine_native`: inspect the selected concrete Engine API,
   generated
   Mechanic contract/Public source, and every supplied engine Example plugin.
   Generate and review the engine-native UI plugin and its tests before moving
   to the next stage.
3. Complete `browser_play`: inspect the selected Browser Serving API, verify
   that this stage's Mechanic bindings and Public paths are empty, and map the
   completed engine-rendered game into the frontend Play surface.
4. Inspect the UI requirement, acceptance criteria, design document, general
   requirement, required screens, and every supplied reference image.
5. Map every acceptance criterion to a UI state, interaction, and meaningful
   target-appropriate UI test. Add Mechanic bindings only for `engine_native`.
6. For `engine_native`, map every visible state to a mocked Mechanic contract
   fixture. Tests must not require real gameplay physics, AI, damage, or
   movement. For `browser_play`, test stream/session/control states through
   Browser Serving fixtures and do not create a Mechanic fixture.
7. Define a clear layout for every required viewport and state.
8. Generate engine-native UI source, resources, configuration, and tests under
   `generated_ui/`, then Browser Play source, resources, configuration, and
   tests under `generated_ui/browser_play/`.
9. Generate `generated_ui/ui_binding_manifest.json` recording the exact
   Mechanic contract version and bindings consumed by `engine_native`.
10. Generate
   `generated_ui/Tests/fixtures/mechanic_contract_fixture.json` with mocked
   contract states/events/command availability used only by engine-native UI
   tests.
11. Generate `generated_ui/screenshot_plan.json` describing every required
   screen, required viewport, fixture state, and expected visible elements
   for both delivery stages that execution must capture.
12. Review text fit, safe margins, contrast, focus, input mode, state
   transitions, and overlap constraints before finalization.

## UI Quality

- Match the game genre, user requirement, and supplied visual references.
- When reference images are supplied, preserve their recognizable visual
  language unless an explicit higher-authority constraint requires a change.
- Keep gameplay information scannable during motion.
- Preserve the view regions explicitly protected by the task.
- Support every required resolution without overlapping critical elements.
- Use stable dimensions and anchors for fixed-format HUD elements.
- Keep text inside its parent at all required resolutions.
- Use familiar controls and icons for commands where supported by the Engine.
- Keep menus, HUD, transient feedback, and terminal states visually distinct.
- Do not add explanatory feature text, debug controls, benchmark labels, or
  implementation notes to the runtime UI.

## Hard Boundaries

- Write only inside the prepared UI workspace.
- Treat Engine Context documents, Mechanic artifacts, task inputs, Skills,
  Prompts, examples, and reference images as read-only.
- Do not modify `meta.json`, `demo_outputs/`, or evaluation artifacts.
- Do not modify the Mechanic artifact or adapter-owned framework source.
- Do not copy Mechanic source into the UI workspace.
- Do not generate empty or placeholder Mechanic-facing interfaces.
- Keep all task-owned output under `generated_ui/`.
- Use only public APIs documented by the selected matching API Reference.
- You MUST generate meaningful target-appropriate UI test source.
- Engine-native UI tests MUST use mocked Mechanic contract fixtures for
  binding, layout, interaction, and screen-state coverage.
- Browser Play tests MUST use Browser Serving API fixtures and MUST NOT create
  or consume the engine-native Mechanic contract fixture.
- You MUST NOT invoke execution or evaluation-only testing APIs.
- You MUST NOT fabricate screenshots or claim that generated UI was rendered.
- You MUST NOT declare benchmark success or assign a score.

## Output Contract

Place task-owned output under:

```text
generated_ui/
    engine-native UI plugin/source/resources
    engine-native UI tests
    ui_binding_manifest.json
    screenshot_plan.json
    Tests/fixtures/mechanic_contract_fixture.json
    browser_play/
        Browser Play source/resources
        Browser Play tests
```

Real screenshots, build reports, runtime captures, and benchmark results belong
to execution and evaluation.

## Repair

When structured failures are provided:

1. Identify the smallest UI-owned root cause.
2. Repair generated UI source, bindings, layout, and tests.
3. Preserve unrelated working behavior and existing evidence.
4. Preserve the ordered delivery plan. Re-read the same Mechanic contract
   version, preserve the engine-native binding manifest, and keep Browser Play
   isolated from Mechanic bindings.
5. Do not change the Mechanic implementation or weaken tests.
6. Report changed files and unresolved risks without claiming execution
   success.
